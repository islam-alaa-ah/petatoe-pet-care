# AM1R1 — إدارة المرفقات — 18.56.145 / Build 185745

حزمة **Modified Files Only** فوق آخر نسخة منشورة **18.56.144 / Build 185744**. طابقت ملفات الاستبدال السبعة النسخة المنشورة بتاريخ 2026-11-09 قبل العمل. هذه مراجعة بديلة لحزمة AM1 غير المثبتة؛ لا تجمع بينهما، ولا تثبتها فوق Schema AM1 موجودة. Migration ترفض التثبيت إذا وجدت الإضافة بالفعل. لم ننفذ تغييرًا أو حذفًا على Production.

## المطلوب الآن فقط

نتيجتا `am1_precheck` و`am1_storage_semantics_audit` اللتان أرسلتهما تمت مراجعتهما. بعد حفظ نسخة قاعدة مناسبة وملفات المشروع الحالية، نفذ **الملفين التاليين فقط، واحدًا بعد الآخر**:

1. `supabase/migrations/20261109090000_am1r1_attachment_management.sql` — تثبيت الإضافة **معطلة**: `enabled=false` و`deletion_enabled=false`.
2. `docs/AM1/sql/01_VERIFY_INSTALL_READONLY.sql` — فحص التعريفات والصلاحيات بعد التثبيت. أرسل ناتج `am1_install_verify` للمراجعة قبل التفعيل.

لا تشغل كل ملفات SQL بالتتابع. لا تستخدم `db push` جماعيًا، ولا تعِد تشغيل Migrations قديمة. ملفات 00 للفحص، و04 لتفعيل مسح لاحق بعد مراجعة منفصلة، و05/06 للتراجع أو الإيقاف عند الحاجة. نجاح Migration وحده ليس إثباتًا لسلامة الوصول أو الأرشيف.

## نتيجة الفحص التي بُنيت عليها المراجعة

- 425 صورة حالية: 423 دليل تركيب، صورة مصروف SEA VIBE، وصورة قالب واتساب. لا صور مؤرشفة في Storage، ولا Delete Markers، ولا مسارات حالية مكررة.
- كل Buckets خاصة، STANDARD، وVersioning معطل. وجود `objects.version` لا يعني تشغيل Versioning؛ لا نغير وضعه.
- 390 صورة تركيب لها سجل مرفق واحد مطابق؛ **33 صورة تركيب بلا سجل مطابق محمية من المسح**. صورة مصروف SEA VIBE مرتبطة لكن الرافع غير مسجل في المرفق، فنميز مالك Storage كقرينة فقط. صورة واتساب محمية دائمًا. العدد المبدئي القابل للمسح بعد الأرشفة هو 391، والمحمي 34، وفق اللقطة المرسلة؛ يُعاد حساب النطاق وقت العملية.
- أرقام البايتات المسجلة قرابة 1.107 GB، وهي بيانات وصفية وليست قياسًا للفوترة أو دليل سبب انقطاع سابق.
- Trigger المنصة يغير `updated_at` عند UPDATE، لذلك لا نستعمله كتاريخ رفع أو جزء من بصمة المحتوى. نعتمد `metadata.lastModified` الصحيح، ثم `created_at` كبديل معلن عند غيابه/عدم صلاحيته. تُحفظ التواريخ الثلاثة ومصدرها منفصلة في الأرشيف.

## ما يظهر في البرنامج

شاشة «إدارة المرفقات» تحت «الإعدادات والخصوصية»، لحساب `super_admin` النشط فقط. قائمة صور Storage الحالية، بكل الشهور أو شهر محدد، 50 صورة لكل صفحة، ومعاينة عند الطلب. يظهر الاسم، صاحب الرفع المسجل أو مالك التخزين المميز، الوقت، العميل، المرجع، المصدر والحجم والبيانات المتاحة. لا نخمن عميلًا أو رافعًا من اسم ملف. الربط المفقود/المتعدد أو الأب المفقود يظل محميًا.

زر أعلى الشاشة ينشئ **PDF واحدًا للشهر المغلق بتوقيت السعودية Asia/Riyadh**، صفحة لكل صورة وبياناتها. كل أصل ثنائي كما رُفع وJSON كامل مرفقان داخل PDF أيضًا؛ معاينة الصفحة فقط مرسومة، وليست نصًا قابلًا للبحث. لا توجد مهمة مجدولة أو قراءة دورية جديدة، ولا طلبات من الشاشة على Dashboard.

التجميع مبني على وقت رفع/استبدال المحتوى، وليس شهر عملية التركيب أو تاريخ المحاسبة. أعداد الشهور في SQL السابق مبنية على تواريخ صفوف Storage؛ راجع تطابقها مع تاريخ المحتوى، خصوصًا الصور عند منتصف الليل بين شهرين. الصورة بلا تاريخ موثق تظهر في «كل الشهور» محمية، ولا تُلحق بشهر بالتخمين.

بعد تنزيل PDF يختار المستخدم **نسخته المحفوظة** من الجهاز. تتم مطابقة الحجم وSHA-256 ثم يؤكد السيرفر الأرشيف. بعدها يظهر زر المسح للأرشيف المؤكد الذي يحتوي صورًا قابلة للمسح، ويظل غير مفعّل ما دام مسح السيرفر مغلقًا. بعد التفعيل يحتاج الزر كتابة الشهر والإقرار بحفظ نسخة ثانية.

## حماية النسخة الأصلية

روابط القراءة موقعة قصيرة العمر ومربوطة برقم نسخة المحتوى. يتم فحص الربط القادم من Storage؛ لو تجاهلت الخدمة `versionId` يفشل التصدير ولا يعتمد PDF للمسح. لا يوجد بديل يقرأ آخر ملف في المسار دون تحديد النسخة.

الحذف يستخدم Storage API بطلب `{path, versionId}` من لقطة السيرفر، ولا يستقبل مسارات من المستخدم ولا يرجع إلى حذف الاسم فقط عند الفشل. صور أحدث، حتى في نفس المسار، لا تدخل طلب الحذف. تغيير المحتوى أو الهوية أو وضع Bucket يوقف العملية. لا يوجد DELETE مباشر على `storage.objects` ولا تعطيل لحماية المنصة.

Trigger واحد إضافي يحمي المسارات المحددة أثناء التصدير/المسح، بما في ذلك كتابات الخلفية التي قد لا تحتفظ بدور JWT للمستخدم. يسمح بتحديث توقيتات الصف فقط، وبحذف نسخة محددة سبق تجهيزها للمسح. أقفال التصدير تنتهي عند النجاح/الإلغاء أو بعد ساعتين. أقفال الحذف غير المحسوم لا تنتهي تلقائيًا. لا يغير Trigger أي ملف خارج اللقطة، ولا يستبدل Triggers المنصة.

## ترتيب النشر بعد فحص 01

1. راجع أن config معطل وrevision=AM1R1؛ RPC الجديدة: anon=false وauthenticated=false وservice_role=true؛ كل دوال Schema الخاصة غير متاحة للمتصفح، وRLS مفعلة وجداولها غير مقروءة له. Trigger الجديد مفعّل، وTriggerا المنصة الأصليان ما زالا كما هما. لا صلاحيات للشاشة الجديدة سوى super_admin.
2. انشر Edge Function `attachment-admin` من `supabase/functions/attachment-admin/index.ts` و`core.mjs`. رفعهما إلى GitHub لا ينشرهما على Supabase. اترك Verify JWT مفعّلًا. مثال بعد ربط المشروع الصحيح: `supabase functions deploy attachment-admin --project-ref YOUR_PROJECT_REF`.
3. أسرار الخدمة تبقى في بيئة Edge: `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY`. لا تُرفع إلى GitHub أو المتصفح. `AM1_ALLOWED_ORIGINS` يسمح بضبط أصول الواجهة الفعلية؛ الافتراضي GitHub Pages الحالي وأصول Capacitor المحلية، دون `*`.
4. افحص Baseline محليًا: `node scripts/am1-preflight-check.mjs baseline /path/to/current-project`. أي اختلاف يستلزم دمجه أولًا؛ لا تستبدل ملفات أحدث. ارفع **محتويات** مجلد الحزمة إلى جذر المستودع بنفس المسارات، دون وضع مجلد AM1R1 حول index.html. تشمل الحزمة ملفات التوثيق والاختبار وملفات جديدة، وليست ZIP مشروع كامل.
5. بعد تطابق Edge/UI/SQL على AM1R1، شغل `02_ENABLE_READ_EXPORT.sql`. يفتح العرض والأرشفة فقط ويترك المسح مغلقًا. اختبر حساب المدير، موظفًا محدودًا، مندوبًا وanon. لا يُعتبر HTTP 200 بقائمة فارغة إثبات أمان وحده.
6. جرّب شهرًا مغلقًا. أغسطس أو سبتمبر كبيران ويحتاجان حفظًا مباشرًا إلى القرص على الكمبيوتر. افتح PDF، راجع كل الصور والبيانات، استخرج الأصول وافحصها واحفظ نسخة ثانية. شغل `03_VERIFY_ARCHIVES_READONLY.sql` وراجع عدم وجود بصمات أو ربط نسخ مفقود.
7. **04 ليست ضمن النشر الأول.** بعد مراجعة نتائج الإنتاج وقبول نطاق المسح وفقد فتح الأصل من الروابط القديمة، يمكن تفعيل المسح بقرار مستقل. SQL التفعيل لا يمسح صورًا؛ المسح الفعلي يحتاج زر الشهر وتأكيده. أول دفعة حقيقية تحتاج مراجعة نتيجتها قبل أي شهر آخر، بما فيها دعم Storage الفعلي لحذف النسخة المحددة. إذا لم تدعم الخدمة الطلب، يتوقف دون حذف بالمسار كبديل.

## الحفظ والحدود

PDF يُحفظ على جهازك، ولا يرفع إلى Storage ولا توجد نسخة منه على السيرفر. حجمه قد يزيد عن مجموع الصور لأنه يحتوي الأصول والمعاينات. التصدير وحده لا يخفض مساحة Storage.

حد الشهر 5,000 صورة و2 GiB أصول، وحد PDF 4 GiB. تنزيل الذاكرة محدود بـ100 MiB أصول و200 MiB PDF؛ للشهور الحالية الكبيرة استخدم حفظًا مباشرًا للقرص على متصفح كمبيوتر يدعم File System Access. معالجة صورة واحدة كل مرة تحد الذاكرة. الصيغة غير المدعومة أو الصورة الكبيرة جدًا أو البيانات التي لا تتسع في صفحة توقف الأرشيف كاملًا. الاختبارات المحلية لا تغني عن اختبار الأجهزة الفعلية والعربية/الإنجليزية وRTL/LTR.

بعد الحذف تبقى سجلات الأعمال والمرفقات، لكن الأصل لن يفتح عبر رابط Storage القديم. الرجوع للصورة يكون من PDF، أو باسترجاع أصلها لنفس المسار. لا تحول الإضافة الشاشات القديمة إلى قراءة PDF المحلي تلقائيًا.

## التراجع

قبل بدء مسح: `05_ROLLBACK_DISABLE.sql` يعطل الإضافة ويحفظ تاريخها، ثم يمكن الرجوع إلى Commit الواجهة 144. لا DROP أو CASCADE. عند وجود مسح غير محسوم، 05 يرفض فتح الأقفال؛ استخدم `06_EMERGENCY_STOP_KEEP_LOCKS.sql` لإيقاف الطلبات الجديدة وراجع النتيجة، فالطلب الجاري قد يكمل. لا تحذف الأقفال ولا تصفر علامات الطلب تلقائيًا.

نسخة قاعدة البيانات وحدها لا تحفظ أصول Storage. احتفظ بنسخة مستقلة مناسبة من الأصول قبل المسح، بالإضافة إلى نسختي PDF. لا يعيد SQL Rollback بايتات محذوفة. لاستخراج الأصول محليًا:

```bash
python3 scripts/am1-extract-archive.py /path/to/archive.pdf /path/to/empty-restore-directory
```

يتطلب `pypdf`؛ يفحص بصمات الأصول ويرفض المسارات غير الآمنة ولا يتصل بالشبكة. استرجاع الإنتاج يتم بعد المراجعة برفع الأصول عبر Storage API إلى نفس Bucket والمسار دون استبدال أصل أحدث. IDs ونسخ Storage وتواريخ الاسترجاع ستكون جديدة؛ الأرشيف القديم لا يصرح بمسحها.

التقرير والأثر والمخاطر والاختبارات بالتفصيل في `docs/AM1/IMPACT_AND_ROLLBACK_AR.md` و`TESTING.md` و`TEST_RESULTS.json`.
