## B01 — اشتراك تنفيذ المواعيد خارج الشاشة

**Root Cause:** في `assets/js/installation-execution.js:80` يُستدعى startRequestRealtime أثناء DOMContentLoaded. وفي `:51` يربط الحدث بمؤقت 250ms ثم load. لا فحص للشاشة الحالية أو ظهور التبويب قبل ذلك التحميل. مخزن requestRealtimeUnsubscribe يمنع بدء اشتراك آخر، لكن لا يوجد استدعاء cleanup في دورة مغادرة الشاشة داخل هذا الملف.

المصدر `assets/js/installations-service.js:1492` ينشئ قناة تتابع UPDATE على installation_requests وكل الأحداث على installation_execution_visits وinstallation_execution_visit_services. لا filter خاص بسجل واحد في القناة؛ ما يصل للمستخدم يظل خاضعًا لحماية Realtime/RLS، فلا يُعد هذا دليل تسريب.

**Impact:** load في `installation-execution.js:75` يطلب executionWorkspace وexecutionIdentity. عند الوصول للشبكة، الأول يبدأ أربع قراءات أساسية في `installations-service.js:516`، والثاني قراءتين في `:649`، وقد تتبعها قراءات سياق/تاريخ فرق/أحياء. وجود كاش أو دمج بعض الطلبات قد يغيّر العدد الفعلي. مؤقت 250ms يدمج دفعة أحداث قريبة، لكنه لا يمنع تحديثات منفصلة متتالية ولا يجعل الطلب خاصًا بالشاشة المفتوحة.

**المحاكاة:** تشغيل ملف التنفيذ الأصلي مع document.visibilityState='hidden' ودون فتح شاشة التنفيذ أنشأ اشتراكًا؛ حدث تحديث مصطنع استدعى محملي workspace والهوية مرة لكل منهما. لا طلب HTTP حقيقي أثناء المحاكاة.

**Scope / Minimal Change المقترح:** تعديل دورة الحياة في ملف الشاشة لبدء الاشتراك عند عرض شاشة التنفيذ للحساب المسموح، وإيقافه عند مغادرتها/إخفاء التبويب/الخروج، وإلغاء مؤقت التحديث المعلق، وقراءة مصالحة واحدة عند الرجوع. تحديث الشاشة المفتوحة يجب أن يستمر، مع حماية من نتائج جلسة أو جيل سابق. لا تغيير في انتقالات التنفيذ أو التحصيل أو SQL أو RLS. لا إزالة لقناة الإشعارات ولا استخدام removeAllChannels.

**قيد تقني مهم:** InstallationsServiceSafe هو Proxy غير متزامن؛ `subscribeExecutionWorkspace` يعيد Promise تنتهي إلى دالة cleanup، وليس دالة مباشرة. أكدته المحاكاة من `installations-service-contract.js:60`. أي إصلاح يجب أن ينتظر الدالة ويعالج المغادرة قبل اكتمال الاشتراك؛ حفظ الـPromise ثم استدعاؤها كدالة سيكسر التنظيف.

## B02 وB03 — فصل الرسم عن تحميل اقتراحات العملاء

**Root Cause:** `app.js:6684` داخل renderDailyOperations يستدعي loadDailySuggestedCustomers. وتُستدعى دالة الرسم من تحميل المهام، وتحديث كاش المهام (`:1138`)، وتغيير اللغة أثناء فتح الشاشة (`:9570`)، ومسارات تحديث أخرى. فالتحميل مرتبط بإعادة الرسم، وليس فقط بطلب مستخدم أو دخول شاشة أو انتهاء صلاحية البيانات.

loadDailySuggestedCustomers في `app.js:6597` يمنع تداخل الدالة الخارجية أثناء انتظارها، لكن DailySuggestionsService يمر عبر KYUMOfflineReadCache. الكاش يرجع القيمة بسرعة ويبدأ تحديثًا غير منتظر؛ بالتالي انتهاء loading الخارجي لا يعني انتهاء تحديث الخلفية.

في `offline-read-cache.js:31–66` يوجد refresh مع كل cache hit، دون شرط cached.stale، ودون سجل in-flight مشترك أو بوابة فشل. لذلك TTL المخزن ليس حدًا أدنى بين طلبات الشبكة. لا يعني ذلك وجود loop لانهائية؛ يعني أن كل مستدعٍ جديد يستطيع بدء طلب جديد، ويتحدد المعدل بالأحداث والمستخدمين والتبويبات.

**Impact:** المسار online في `daily-suggestions-service.js:38` يستدعي get_daily_customer_suggestions ثم يقرأ status من daily_customer_suggestions. بعض تعريفات SQL في المشروع تستدعي replenish_daily_customer_suggestions داخل RPC القراءة، مثل `phase_p5_12_8_daily_suggestions_runtime_definition_recovery.sql:215`. إذًا لا نتعامل معه كقراءة عديمة الأثر، ولا نشغله كفحص تشخيصي اصطناعي. تعريف Production الحالي لهذه الدوال غير مستخرج في هذه المراجعة، وترتيب ملفات SQL التاريخية غير مثبت.

**المحاكاة:** قراءتان متتاليتان لكاش حديث شغّلتا loader مرتين، وقراءتان متزامنتان لنفس المستخدم والمفتاح بدأتا loader مرتين قبل اكتمال الأولى.

**Minimal Change:** أولًا إزالة الجلب من الرسم وربطه بالتفعيل والتحديث والإبطال الحالي؛ ثم دمج الطلب الجاري في الكاش حسب namespace+key. تعديل معنى force أو TTL أو fallback قرار لاحق؛ يجب أن يظل التحديث بعد تسجيل متابعة و«تم التواصل» صحيحًا. لا تعطيل تقرير توزيع العملاء حسب آخر بيع، ولا تغيير أهليّة العملاء أو دورة الاقتراحات.

## B04 — فحص count للعملاء

**Root Cause:** `customers-service.js:171` ينفذ `.select('id',{count:'exact',head:true})`. تستدعيه refreshCustomersInBackground في `:219` قبل Delta Sync؛ وفحص الكاش في `:294` لا يشترط أن يكون قديمًا لبدء تلك الخلفية.

**Impact:** هذه قراءة عدد الصفوف المرئية للحساب وفق RLS، وليست قراءة أسماء أو هواتف. إذا اختلف العدد عن الكاش، يمسح حالة المزامنة ويجبر full sync. لذلك إزالة الفحص عشوائيًا قد تفقد آلية إصلاح كاش غير متطابق. اختلاف عدد صحيح قد يستدعي أيضًا إعادة تحميل كل صفحات العملاء، 250 صفًا للصفحة.

**الدليل التشغيلي:** SQL الخطأ الذي أرسله المستخدم يعدّ customers بالكامل داخل pgrst_source_count، دون LIMIT على العدّ. LIMIT في جزء صفحة البيانات لا يحد هذا count. نعرف أن الطلب انتهت مهلته؛ لا نعرف بعد لماذا تجاوز المدة: تكلفة RLS، خطة القراءة، الحمل، أو انتظار موارد.

**Minimal Change:** بوابة واحدة للمصالحة حسب المستخدم، مع دمج الطلب الجاري وفاصل محسوب/تراجع بعد فشل العدّ، والحفاظ على tombstones والـfull sync عند الحاجة. لا استبدال العدد بتقدير داخل فحص يعتمد على التطابق، ولا رفع timeout العام، ولا فتح RLS كحل أداء.

كل مسار يقرأ صفحات 500، بحد أمان 200 صفحة؛ هذا سقف وليس عددًا يستهلكه كل مستخدم. تحميل نفس تاريخ المبيعات أكثر من مرة فرصة لتوحيد المصدر، لكن حذف pagination أو الاكتفاء بصفحة أو تغيير SUM سيكسر اكتمال التقارير؛ لا تعديل مالي ضمن هذه المراجعة.

## B10 وB11 — أحمال مطلوبة أو تحتاج قرارًا منفصلًا

- System Health: مؤقت 30 ثانية في `app.js:4017`؛ يتوقف عند مغادرة شاشة systemHealth في switchView، فلا يعمل من كل الشاشات باستمرار. الفحص ينظر إلى إخفاء القسم، ولا يفحص document.visibilityState؛ متصفح بخلفية قد يستمر مع خنق المتصفح للمؤقت. 120 استدعاء/ساعة هو المعدل النظري إذا استمر المؤقت دون خنق، وليس قياس Production. دالة SQL الموجودة بالمشروع تستخدم إحصاءات reltuples لمعظم الجداول، وليست COUNT كاملًا لكل جدول؛ لا نضخم سبب الحمل.
- الحضور اليومي: heartbeat كل 5 دقائق فقط عند ظهور التبويب والتفاعل خلال آخر 15 دقيقة (`daily-activity-service.js:66`). مصدر تقارير حضور/نشاط حالي، وليس ميزة مهجورة. لا إيقافه لتقليل Logs دون قرار تشغيلي.
- الإشعارات P3: مصدره الحالي يدمج القراءة/الأحداث، ويؤخر REST أثناء اتصال Realtime إلى مصالحة 15 دقيقة، مع fallback وفشل متراجع. اختبار المستخدم أثبت قناة إشعارات واحدة في التبويب؛ لا يثبت أن إجمالي قنوات التطبيق واحدة، لأن قناة التنفيذ منفصلة. لا نعيد فرضية polling القديم على P3.
- Push: `notification-center.js:128` و`notification-center-service.js:265` و`:315` تستدعي dispatcher عند البدء وبعد emit، إذا كان Push مدعومًا ومهيأ. config له كاش خمس دقائق. فحص P3-AUDIT-02 السابق لم يجد enqueue داخل emit الحالي أو triggers على الجدولين؛ قد توجد تكاملات خارجية غير مفحوصة. الاستدعاء لا يثبت وصول رسالة، ولا يجوز تشغيل dispatcher كفحص لأنه قد يرسل Push فعليًا. يبقى مسارًا منفصلًا عن أمان Views.
- metadata الخاصة بالـsync والـtombstones لها ACKs وthrottle وصيانة يومية بالمصدر (`sync-retention.js`). إزالة هذه العمليات قد تضر إثبات حدود إعادة التشغيل والحذف دون اتصال. لا تعديل أو تشغيل prune ضمن الفحص.

الـView العادية لا تعيد حساب نفسها في الخلفية لمجرد وجودها؛ تُنفذ عند الرجوع إليها باستعلام. لذلك حذف View غير مستدعاة لا يزيل حمل تقارير دوريًا مفترضًا. هذا لا يقلل أهمية تحذيرها الأمني: التعرض عبر API والمنح موضوع مستقل عن الاستدعاء من واجهة التطبيق.

## علاقة النتائج بارتفاع Logs

زيادة الطلبات الفعلية والأخطاء قد تزيد Logs Ingest، لأن Supabase يجمع سجلات من عدة خدمات. أما Logs Query فيقيس مسح السجلات في واجهات قراءة Logs. لم نجد في JS/Edge Functions المفحوصة استدعاءً ظاهرًا لواجهة إدارة/استعلام سجلات Supabase. هذا لا يحصي استهلاك Dashboard أو السكربتات أو المستخدمين الآخرين أو مشاريع المؤسسة الأخرى.

لذلك لا يجوز نسبة قفزتي 1 و2 نوفمبر أو 118.58GB من Logs Query إلى View أو خدمة بعينها بناء على المراجعة الحالية. يلزم ربط نافذة زمنية ضيقة بمصدر السجلات، endpoint، حالة HTTP، والمستدعي. الفحص المرفق لا يولد استعلام Logs جديدًا، ولا يغير إعدادات log_statement أو retention.

## اختبارات القبول المطلوبة لأي إصلاح لاحق

1. Admin، موظف محدود، مندوب، حساب بلا صلاحية التنفيذ أو التقارير، وanon. استخدام حسابات مشروعة، دون تغيير أدوارها لاجتياز الفحص.
2. البدء على dashboard، ثم فتح التنفيذ/مغادرته/الرجوع إليه، وإخفاء تبويب المتصفح والعودة، والتنقل السريع أثناء فتح الاشتراك. لا توليد انتقال تحصيل أو فاتورة لاختبار الاشتراك.
3. تبديل المستخدم والخروج والدخول: لا قناة أو نتيجة من المستخدم السابق. تبويبان مستقلان: لا نفترض أن دمج الطلبات داخل tab ينسق عبر جميع التبويبات.
4. الإشعارات P3: استمرار الجرس وحالة القراءة والتحديث المتوقع؛ إزالة قناة التنفيذ لا تمس قناة الإشعارات.
5. Offline/online وإعادة تشغيل queue المصرح بها: أول فتح شاشة يحصل على أحدث نطاق وبيانات، والحذف/الـtombstones/التعارضات لا تتأثر. لا تنفيذ عمليات مالية تجريبية في Production.
6. المهام اليومية و«تم التواصل» وآخر بيع: ترتيب العملاء، حالة التواصل، WhatsApp، وعدد الاقتراحات يظلون صحيحين وفق الصلاحية الحالية.
7. تقارير المبيعات/الأداء والعقود وCustomer 360: نفس الحساب والفلاتر والفترة والمصدر، دون نقص بسبب paging أو حذف preload معتمد عليه.
8. العربية والإنجليزية، Desktop/Tablet/Mobile، Light/Dark؛ اختبارات مشاهدة/تنقل وقراءة جديدة مناسبة للتغيير، دون حزمة UI إضافية.
9. مقارنة عدد الطلبات ومدتها في سيناريو مماثل قبل كل خطوة وبعدها؛ عدد endpoint مكرر وحده لا يثبت أن طلبين لهما نفس filters/method. ثم متابعة الأخطاء وLogs لنفس النافذة/المصدر، دون بحث واسع متكرر.

## الاختبارات المنفذة وحدودها

- حصر ملفات وروابط script/routes ومواضع literal from/rpc/channel والتوقيتات ودورات التفعيل؛ موجود في SOURCE_INVENTORY.json. هذا حصر نصي، لا محلل call graph كامل ولا قياس traffic.
- ثماني محاكاة ناجحة أعادت إنتاج سلوك المصدر الأصلي: التنفيذ بالخلفية، Promise cleanup، تحديث كاش حديث، عدم دمج قراءتين متزامنتين، count العملاء، تكرار scope، خزينة غير مفتوحة، ونطاق مواعيد بلا سياقات. النتائج في LOCAL_TRACE_RESULTS.json مع hashes الملفات.
- اجتاز سكربت الالتقاط فحص syntax وفحصًا محليًا لعدم إخراج query strings/أسماء قنوات/معرفات/مفاتيح، وعدم بدء أي اتصال. بيانات الاختبار مصطنعة.
- لم تُجر محاكاة PostgreSQL، ولم تُنفذ SQL أو HTTP/RPC أو عمليات حفظ على المشروع بواسطة المساعد. لم تُختبر UI أو الحسابات الحية أو CPU/خطط التنفيذ أو Security Advisor من جديد ضمن هذا الفحص.
- إعادة إنتاج طلب زائد لا تثبت نسبة مساهمته في فاتورة أو انقطاع سابق. البيانات الموجودة في المتصفح قد تكون محذوفة من resource buffer، ولا تقيس CPU أو رسائل WebSocket أو مستخدمين آخرين.

## حالة المسار الأمني

SEC-S2.01 وسحب anon SELECT من customer_followup_summary يبقيان كما أرسل المستخدم. SEC-S3.01 على quotation_status_report يبقى مفعّلًا كما أكد Apply وVerify؛ التحذير الخاص به غاب من القائمة المعروضة، وتبقى سبعة مستهدفة. اختبارات النطاق والحسابات ذات بيانات معروفة لم تكتمل.

فحص الحمل لا يغير RLS أو EXECUTE أو الأدوار، ولا يغلق ملاحظات S4/S5. لا نعالج تحذير View بالحذف لمجرد عدم وجود شاشة باسمها، ولا نجمع تحسينات الحمل مع SQL الأمان في مرحلة تنفيذ واحدة.
