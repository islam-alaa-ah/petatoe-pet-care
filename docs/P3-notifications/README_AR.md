# PETATOE — P3: استقرار الإشعارات ومنع التكرار

**الحالة: حزمة معدّة للمراجعة والتطبيق؛ لم تُنشر ولم تُشغّل استعلامات على Production.**

- الإصدار: `18.56.141`، Build `185741`، تاريخ الإعداد: 7 نوفمبر 2026.
- Baseline المعتمد: أحدث ملف `petatoe-pet-care-main(1).zip`، الإصدار `18.56.140`.
- SHA-256 لملف ZIP الأصلي: `86e0a009a4f80706086ee8022f3441fbb33817d78eb801b2645506acbc80de82`.
- التسليم: Modified Files Only، داخل مجلد مرحلة واحد. لا توجد ملفات قديمة غير معدلة داخل الحزمة.

## Root Cause

الكود كان يستخدم Supabase Realtime بالفعل. المشكلة ليست غياب WebSocket:

1. الواجهة تضيف كل INSERT باستخدام `unshift` دون دمج حسب `notification.id`؛ يمكن عرض السجل نفسه أكثر من مرة عند تداخل القراءة مع الحدث المباشر.
2. بدء الاشتراك من أكثر من حدث تهيئة يعيد الاشتراك ويرسل طلبات إضافية. الإلغاء السابق لا ينتظر اكتمال إزالة القناة.
3. يستمر التحديث كل 60 ثانية أثناء اتصال Realtime. القراءة من Cache تطلق تحديثًا خلفيًا يبتلع الخطأ، فلا يصل فشل هذا المسار إلى Backoff الواجهة.
4. طلبات القراءة الجارية كانت مفهرسة بالحد فقط، مع تحديد مساحة Cache عند انتهاء العمل؛ هذا يسمح بسباق عند تبديل الحسابات.
5. الاشتراك السابق يستقبل INSERT فقط، فلا يستقبل تحديث حالة القراءة من جهاز آخر مباشرة.
6. مسارا تعديل الموعد وتعديل مساحة الإكمال ينشئان مفتاح حدث من وقت الإرسال؛ المحاولة المتزامنة أو إعادة نفس كائن الطلب قد تُنتج مفاتيح مختلفة.

هذه نتائج من الكود. لا تثبت أن هذه المسارات وحدها سببت ارتفاع Log Ingestion يومي 1 و2 نوفمبر. ولا تثبت سبب استهلاك Log Query.

## Impact Analysis وScope

| المسار | الأثر المقصود | ما يلزم التحقق منه على Production |
|---|---|---|
| جرس الإشعارات | دمج حسب ID؛ السجلات المختلفة تظل مستقلة حتى لو تطابق النص | وصول إشعار مشروع مرة واحدة في القائمة |
| اتصال Realtime | قناة واحدة لكل حساب داخل كل تبويب؛ إزالة القديمة قبل الجديدة | INSERT وUPDATE متاحان ضمن إعداد النشر الحالي |
| تحميل القائمة | قراءة أولية، ثم مراجعة كل 15 دقيقة أثناء الاتصال السليم | ظهور أحدث السجلات المسموح بها للمستخدم |
| الانقطاع | REST احتياطي كل دقيقة بعد القراءة الناجحة؛ Backoff عند الفشل | استمرار التحديث عند تعطّل Realtime دون عاصفة طلبات |
| حالة القراءة | تحديث فوري محلي ودمج UPDATE من الأجهزة الأخرى؛ إعادة الحدث القديم لا تلغي القراءة | جهازان للحساب نفسه |
| تعديل الموعد/مساحة الإكمال | مفتاح ثابت للمحاولة نفسها باستخدام كائن Payload نفسه؛ نجاح العملية ينهي المحاولة | كل حفظ جديد مشروع يولد حدثًا مستقلاً وفق الإعدادات |
| التحديث/PWA | توحيد رقم الإصدار وCache، ووصف الإصدار بالعربية والإنجليزية | وصول الملفات الجديدة بعد تحديث التطبيق |

لا تتغير استدعاءات RPC للعمليات التجارية أو قيمها أو التحقق منها أو ترتيبها. تعديل `installations-service.js` محصور في هوية حدث الإشعار في المسارين المحددين. مفاتيح العمليات المالية القائمة بقيت كما هي.

لم تتغير الأدوار أو الصلاحيات أو RLS أو مستلمو الأحداث أو إعدادات الإشعارات أو منطق Web Push. لم تتغير ملفات CSS أو سلوك اللمس والتموضع الخاص بالجرس. حزمة P3 منفصلة عن مراحل SEC؛ لا تُغلق تحذيرات Security Definer ولا تعيد منح `anon` أي صلاحية سُحبت سابقًا.

## SQL المطلوب وترتيب التنفيذ

**لا يوجد SQL تغييري أو Migration مطلوب لتنفيذ P3.** ملف `phase_p3_notifications_realtime_readonly.sql` فحص قرائي اختياري قبل النشر، عبارة عن SELECT واحد يعيد Metadata في JSON دون بيانات العملاء. لم يُشغّل ضمن تجهيز الحزمة.

1. تأكد أن هذه هي آخر نسخة منشورة وأنه لا يوجد تعديل أحدث على الملفات الثمانية. من مجلد الحزمة المستخرج، افحص نسخة المشروع الحالية قبل نسخ أي ملف:

   ```bash
   node scripts/p3-preflight-check.mjs baseline /absolute/path/to/current-app
   ```

   المطلوب PASS للملفات الثمانية. عند FAIL توقف؛ يجب المطابقة مع أحدث Baseline قبل الاستبدال. السكربت قرائي ولا يعدّل الملفات.

2. احتفظ بنسخة مستقلة من الملفات الثمانية الحالية بمساراتها، ونسخة الإصدار المنشور في الاستضافة إن توفرت. احتفظ بنتيجة Preflight وبقيم SHA-256 من `manifest.json`. هذه هي نسخة التراجع.

3. راجع Metadata الحالية للإشعارات: عضوية `public.notifications` في `supabase_realtime` مع `pubinsert=true` و`pubupdate=true`؛ بقاء RLS وسياسة القراءة الخاصة بالمستخدم؛ وتعريف دالة الإرسال وقيد UNIQUE على `dedupe_key` مطابقين للتوقعات. الاستعلام المرفق يستخرج هذه المعلومات فقط. صفر صفوف أو تعريف مختلف يستلزم تقييمًا مستقلاً؛ لا تُغيّر Publication أو Grants أو RLS لحل النتيجة تلقائيًا.

4. سجّل القياس السابق للتحديث: عدد طلبات `notifications` في Network، عدد القنوات، وعدد الإشعارات غير المقروءة لكل حساب مصرح. لا تجمع بيانات العملاء في تقرير الاختبار.

5. حدّث الملفات الثمانية كإصدار واحد عبر آلية النشر المعتادة التي تسمح باستعادة الإصدار السابق. عند النقل اليدوي ارفع ملفات JS و`package.json` أولاً، ثم `index.html` و`service-worker.js`، واجعل `version.json` آخر ملف. لا تترك حالة الملفات المختلطة مفتوحة للاستخدام؛ النشر الذري هو الأفضل. ملفات `scripts` و`docs` للتحقق والتوثيق، وملف SQL ليس ملفًا للتطبيق التلقائي.

6. افحص النسخة المحدثة:

   ```bash
   node scripts/p3-preflight-check.mjs installed /absolute/path/to/current-app
   npm run check:p3
   ```

   افحص أن `window.KYUM_RELEASE_VERSION` يساوي `18.56.141` وأن `NotificationCenterService.runtimeVersion` يساوي `P3` بعد تحديث التطبيق. لا تمسح Local Storage أو IndexedDB أو الطابور غير المتزامن.

7. نفّذ اختبارات Production أدناه، وتوقف عند أول أثر غير متوقع. لا تعتمد نجاح رفع الملفات أو PASS السكربت وحده كإثبات نجاح Production.

## الاختبارات المنفذة فعليًا

- **17/17 اختبارًا محليًا ناجحًا** عبر Node مع Supabase ووقت وأحداث وCache وهمية؛ لا اتصال بقاعدة البيانات. يشمل التكرار، السباق بين Snapshot والأحداث، حالة القراءة، تبديل الحساب، الخروج Offline، القناة الواحدة، تعطل Realtime، Backoff مع Cache، وسلامة مفاتيح الأحداث.
- فحص بناء JavaScript للملفات المعدلة وسكربتات التحقق.
- فحص 1,155 ملف Baseline: تغيرت 8 ملفات فقط، وبقيت 1,147 مطابقة. جميع ملفات CSS الـ31 وملفات SQL الأصلية الـ421 بقيت مطابقة.
- مقارنة مصدرية أثبتت تطابق منطق `installations-service.js` بالكامل بعد استثناء سطور هوية الإشعار المحددة. دوال المصفوفة وWeb Push ومعالجات لمس الجرس بقيت مطابقة.
- أدوات التحقق التاريخية تتضمن حالات فشل موجودة في Baseline نفسه. فحص المصفوفة وجرس الموبايل أعادا حالات الفشل نفسها. فحص تقارير المبيعات أضاف فشل فحوص الإصدار القديم نتيجة ترقية الإصدار فقط، مع بقاء حالتي الفشل الأصليتين. التفاصيل في `TEST_RESULTS.json`؛ لم تُصلح هذه الحالات ضمن P3.
- **اختبار Chromium المرئي لم يعمل**: بيئة التشغيل رفضت إنشاء socket عند تشغيل المتصفح (`Operation not permitted`). لذلك Desktop/Tablet/Mobile × AR/EN × Light/Dark **ليست مُعتمدة بصريًا**. سكربت الفحص المرفق يجهز الحالات الـ12 محليًا دون اتصال Supabase، لكنه لم ينجح في التشغيل هنا، ويجب تشغيله في بيئة مناسبة أو إجراء الفحص يدويًا.

تشغيل الفحص المرئي في جهاز تطوير مجهز بـ Playwright وChromium:

```bash
node scripts/p3-notifications-browser-check.mjs
```

يمكن تحديد مسار Playwright عبر `P3_PLAYWRIGHT_MODULE` ومسار Chromium عبر `P3_CHROMIUM`. لا تثبيت لمكتبات أو تغيير لاعتماديات Production ضمن هذه الحزمة.

## Rollback

محفز التراجع: فقد إشعارات مصرح بها، ظهور حساب آخر، تعطل الدخول/الجرس، أو زيادة غير متوقعة في الطلبات مرتبطة بالإصدار.

1. أوقف تعميم الإصدار وأعد نسخة النشر السابقة، أو أعد الملفات الثمانية التي أخذت نسختها قبل التطبيق كإصدار واحد.
2. تحقق من مطابقتها باستخدام وضع `baseline` في سكربت Preflight من نسخة الحزمة المحتفظ بها خارج المشروع.
3. أعد تحميل العميل وتحقق من عودة `18.56.140`. زر التحديث قد لا يقترح الرجوع إلى إصدار أقل. عند استمرار Cache الجديد، استخدم إجراءات تحديث/إعادة تحميل التطبيق؛ وللمسؤول التقني من Console، الدالة القائمة `KYUM_UPDATE.clearCaches()` تمسح Cache التطبيق فقط، ثم `KYUM_UPDATE.reload()` يعيد التحميل. لا تستخدم Clear Site Data ولا تمسح بيانات الطابور أو التخزين المحلي.
4. اختبر الدخول والقائمة واستلام إشعار مشروع وحالة القراءة مجددًا.

لا يوجد Rollback لقاعدة البيانات في P3 لأن الحزمة لا تغيّرها. الإشعارات التي أُنشئت وحالة القراءة التي حدّثها المستخدم أثناء الاستخدام تبقى في قاعدة البيانات؛ لا تحذفها عند التراجع. لا تُشغّل Rollback المرحلة الأمنية SEC-S2.01 بسبب تحديث P3.

## المخاطر المتبقية وحدود النتيجة

- اختبارات المستخدمين الحقيقيين والـRLS وPublication وPush وPWA والأجهزة الفعلية لم تُنفّذ هنا.
- لا حذف أو دمج للإشعارات التاريخية ذات IDs مختلفة؛ تطابق النص وحده لا يثبت أنها مكررة.
- هذه ليست ضمانة Exactly Once لكل عملية تجارية عبر إعادة تحميل الصفحة أو كائن Payload جديد أو تبويب آخر. منع تكرار السجل على الخادم يعتمد على تعريف الدالة وقيد `dedupe_key` الحاليين. الآلية الجديدة تحد المحاولات المتزامنة بالهوية نفسها داخل الجلسة، ولا تعيد تصميم RPCs التجارية أو Outbox.
- تغيير مفاتيح تعديل الموعد/الإكمال يحتفظ بالمفتاح عند إعادة نفس Payload بعد الفشل، وينهيه عند نجاح العملية. حفظ مشروع جديد يأخذ مفتاحًا جديدًا، حتى عند تطابق المحتوى؛ لا توجد نافذة زمنية تمنع تعديلات صحيحة.
- إذا تعطل استقبال الأحداث دون أن تظهر حالة خطأ من Realtime، فالمراجعة الاحتياطية تلتقط البيانات خلال نحو 15 دقيقة في تبويب ظاهر ومتصل. عند فشل REST تعمل مهلة Retry، فلا يوجد وعد بتسليم فوري أثناء تعطل الخدمات.
- التبويبات أو التطبيقات المفتوحة بالإصدار القديم تستمر بسلوكها إلى أن تُحدّث. لا يُقاس الانخفاض المتوقع في طلبات الجرس قبل التأكد من النسخ الفعالة.
- WebSocket نفسه له استهلاك. تقليل طلبات هذا المسار لا يضمن اختفاء Log Ingestion ولا يخفض تلقائيًا Log Query الناتج عن فحص السجلات. التحقيق في طفرتي 1 و2 نوفمبر يظل مسارًا مستقلاً.
