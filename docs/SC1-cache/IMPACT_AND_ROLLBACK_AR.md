# SC1-SMARTCACHE-RECOVERY — تقرير الأثر والتراجع

## الحالة وحدود الدليل

الأساس المؤكد هو النسخة `18.56.143 / 185743` بعد P3 وP4 وP5. أكد المستخدم أن المحتوى المرسل هو `smart-cache.js`. جرى جلب الملفات الستة المستهدفة المنشورة من رابط البرنامج العام ومطابقتها مع شجرة 18.56.143 قبل إعداد التعديل. هذه مطابقة لتلك الملفات، وليست مراجعة كاملة لكل ملفات المستودع أو لكل استجابة مخزنة بمتصفح المستخدم.

النسخة الناتجة `18.56.144 / 185744`، بتاريخ 2026-11-08. الحزمة مجهزة محليًا فقط؛ لم يُنشر تعديل بواسطة المساعد ولم يُنفذ SQL تغييري.

الدليل الحي المتاح قبل SC1:

- SQL Editor استجاب بتاريخ 2026-11-08 12:48 UTC (14:48 بتوقيت القاهرة): PostgreSQL 17.6، حجم القاعدة 48 MB، 24 اتصالًا مرصودًا في القاعدة، و`max_connections=60` للخادم، وانتظار أقفال ومعاملات idle in transaction بصفر. الإعداد `default_transaction_read_only=off` يخص جلسة/دور الفحص، ولا يثبت غياب قيود لكل الأدوار والمسارات.
- فحص Auth health أعاد 200، وفحص Data API على `notifications?select=id&limit=0` أعاد 200 ومصفوفة فارغة. لم تُقرأ سجلات مستخدمين أو يُطلب count exact. فحص جذر REST طلب مفتاحًا سريًا، فلم يُستخدم للحكم على صحة استعلامات البرنامج؛ لم يُطلب مفتاح سري.
- بعد إعادة التحميل أرسل المستخدم `configured=true` و`clientReady=true` و`authInitialized=true` و`authOffline=false`، مع استمرار رسائل فشل كتابة SmartCache في الصورة الجديدة.

هذه الأدلة لا تثبت انقطاع PostgreSQL بسبب Storage ولا تثبت سبب اختفاء علامة bootstrap سابقًا. بدء برنامج Supabase عاد بعد إعادة التحميل؛ SC1 يستهدف عيب تعافي SmartCache المثبت، ولا يدّعي إصلاح السبب الأول لفشل التهيئة السابق أو سبب الإغلاق الأول للـIndexedDB.

## Root Cause — السبب المثبت

كانت `openDatabase()` تحتفظ بـPromise واحدة طوال عمر التبويب. بعد نجاح الفتح تشير تلك Promise إلى نفس كائن `IDBDatabase`، حتى إذا صار الاتصال مغلقًا أو قيد الإغلاق. لا توجد معالجة لإبطال هذا المرجع عند `close` أو `versionchange`، ولا إعادة فتح عند فشل إنشاء transaction بسبب `InvalidStateError`.

لذلك تعيد `get` و`set` و`removePrefix` وغيرها محاولة إنشاء transaction على نفس الاتصال المغلق. المصدر يمسك بعض الأخطاء ويطبع تحذيرًا ويستخدم ذاكرة التبويب عند الإمكان، لكنه لا يصلح الاتصال، فتتكرر التحذيرات. أُعيد إنتاج الحالة محليًا بالمصدر الأصلي، ثم اختُبر التعافي بالمصدر المعدل.

كما وُجد في المصدر أن فشل فتح قاعدة الكاش يتحول إلى Promise محفوظة ترجع null باستمرار، وأن طلب فتح blocked قد ينجح لاحقًا بعد رجوع المستخدم إلى الذاكرة دون إدارة ذلك الاتصال المتأخر. هذه نقاط فُحصت محليًا؛ لم يثبت أنها كانت مُشغّل العطل في جهاز المستخدم.

مرجع سلوك المنصة: [IndexedDB specification](https://www.w3.org/TR/IndexedDB/) و[IDBDatabase.transaction](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction). إنشاء transaction على اتصال close-pending يرفض بـInvalidStateError، وحدث close لا يغطي كل إغلاق صريح، لذلك توجد حماية عند نقطة إنشاء transaction أيضًا.

## Impact Analysis — الاعتماديات والأثر

SmartCache مخزن محلي مشترك لقراءات وخدمات عديدة، ومنها العملاء والمتابعات والعمليات اليومية والإشعارات وworkspaces المالية. إصلاح الاتصال يجب أن يحافظ على واجهته العامة والبيانات ومفاتيح المستخدمين، دون تعديل المستهلكين أو إعادة إرسال عمليات عمل إلى الخادم.

| العنصر | السلوك بعد SC1 |
| --- | --- |
| اتصال كاش يعمل | يُعاد استخدامه؛ الطلبات المتزامنة تشترك في فتح واحد |
| اتصال مغلق دون حدث close | إعادة فتح مرة واحدة إذا فشل **إنشاء** transaction بـInvalidStateError |
| إغلاق مفاجئ مع حدث close | إبطال المرجع؛ العملية التالية تفتح اتصالًا جديدًا |
| فشل اتصال جديد أيضًا | انتهاء المحاولة مع تهدئة خمس ثوانٍ، ثم يسمح لعملية لاحقة بمحاولة فتح؛ لا يوجد timer أو polling جديد |
| transaction بدأت بالفعل | لا يعاد تشغيلها أو إعادة تنفيذ put/delete/cursor تلقائيًا عند فشلها |
| طلب blocked | استخدام fallback؛ طلب الفتح القديم إذا تأخر لا يصبح اتصالًا غير مُدار، ولا ينفذ ترقية متأخرة بعد إلغائه منطقيًا |
| versionchange من تبويب آخر | إغلاق الاتصال لإتاحة الترقية/الحذف؛ الصفحة القديمة تستخدم الذاكرة وتنتظر إعادة تحميل بدل منازعة إصدار آخر |
| فشل تخزين آخر مثل QuotaExceededError | لا يُصنّف كاتصال مغلق ولا يبدأ إعادة فتح/إعادة كتابة تلقائية |

تُوضع طلبات القراءة/الكتابة في transaction بصورة متزامنة فور إنشائها. لا يضاف await بين إنشاء transaction وإرسال عملياتها، للحفاظ على فترة نشاطها.

تظل قاعدة `kyum_crm_smart_cache` بإصدار **1** ومتجر `entries` والفهارس القائمة. تظل خوارزمية hash وnamespace وTTL وشكل metadata ونسخة الواجهة القديمة `M13.5` كما هي، مع إضافة `runtimeVersion: SC1` ومراقبة اتصال سلبية دون بيانات حسابات. لا توجد إعادة تسمية أو حذف قاعدة أو ترحيل بيانات في SC1.

Offline Queue يستخدم مساره القائم ولم يُعدل. جرى اختبار أن إعادة فتح مخزن الكاش لا تمس قاعدة أخرى تحتوي سجل pending معزولًا، مع مطابقة ملف Offline Queue نفسه للأساس. لا يعني ذلك ضمان استرداد بيانات حذفها المتصفح خارجيًا.

## Scope — الملفات والتغيير المحدود

كل ما عدا الملفات الستة من أساس 18.56.143 مطابق بايتًا ببايت. لا تغيير في SQL أو RLS أو أدوار المستخدمين أو SDK bootstrap أو منطق الرواتب والعمولات والفواتير أو شاشات البرنامج أو CSS. تفاصيل البصمات وحدود المقارنة في SOURCE_INTEGRITY وmanifest.

## SQL وترتيب التنفيذ

**SQL مطلوب: لا.** كل محاكاة الإغلاق وعمليات put/delete التجريبية أجريت على تنفيذ IndexedDB وهمي داخل ذاكرة Node، وليس على Chrome أو Supabase أو بيانات Production.

1. احتفظ بـcommit/ZIP الإصدار 18.56.143 الذي يعمل حاليًا.
2. شغّل فحص baseline من مجلد الحزمة، وراجع أي اختلاف قبل الاستبدال.
3. انقل الملفات المعدلة والمضافة إلى مساراتها الأصلية في commit واحد، ثم شغّل installed محليًا.
4. انشر بالطريقة المعتادة، وتحقق من رقم 18.56.144 **ومن runtime SmartCache=SC1 معًا**.
5. نفذ اختبارات Production أدناه قبل اعتبار عيب التعافي مغلقًا. لا تكفي رسالة نجاح الرفع أو اختفاء تحذيرات قديمة من Console.

## الاختبارات المنفذة

- SC1: **35/35 ناجحة** بالمصدر الحقيقي وتنفيذ IndexedDB في الذاكرة `fake-indexeddb@6.2.7`. تشمل read/write/remove/prefix/stats بعد إغلاق صريح ومفاجئ، القراءة من بيانات محفوظة في صفحة سابقة، 40 كتابة متزامنة وترتيبها، late events، blocked وlate success، ترقية تبويب آخر، open failure/backoff، abort، quota failure، namespace وTTL وhash وواجهة metadata.
- P5: **38/38 اختبارات سلوك ناجحة** مع استبعاد اختبار نسخة الإصدار 18.56.143 التاريخي فقط.
- P4: **27/27 ناجحة**.
- P3: **16/16 اختبارات سلوك ناجحة** مع استبعاد اختبار نسخة الإصدار 18.56.141 التاريخي فقط.
- الإجمالي **116 اختبارًا ناجحًا**. تطابق بيانات الإصدار 18.56.144 مفحوص في SC1، ولا تُعدل الاختبارات التاريخية لتغيير ما كانت تثبته.
- أداة الالتقاط اختُبرت دون فتح IndexedDB أو إرسال طلب أو تغيير listeners. فحص صياغة الملفات والمقارنة والتركيب ضمن فحوص الحزمة.

المحاكاة ليست متصفحًا فعليًا ولا تعيد إنتاج كل أخطاء نظام الملفات أو حدود التخزين في Chrome/Safari. فحص واجهة بصري فعلي لم يُنفذ هنا؛ تشغيل Chromium في البيئة كان محظورًا بخطأ socket EPERM في العمل السابق، ولم تُعَد محاولة تشغيله. فحوص الأجهزة والثيمات والحسابات الحية تظل مطلوبة.

لتكرار اختبارات SC1 محليًا باستخدام Node 24، ثبّت تبعية الاختبار في مجلد مؤقت خارج المستودع:

```bash
npm install --prefix /tmp/petatoe-sc1-tests --ignore-scripts --no-audit --no-fund fake-indexeddb@6.2.7
PETATOE_SC1_TEST_MODULE=/tmp/petatoe-sc1-tests/node_modules/fake-indexeddb node --test scripts/sc1-smart-cache-recovery.test.mjs
```

هذه التبعية لا تُرفع مع البرنامج ولا تُضاف إلى package.json. المصدر الرسمي: [fakeIndexedDB](https://github.com/dumbmatter/fakeIndexedDB).

## اختبارات Production المطلوبة

1. التقط `scripts/sc1-live-readonly.js` بعد اكتمال النشر والتحميل. يجب أن يظهر 18.56.144 وSC1، وأن يبقى تسجيل الدخول طبيعيًا، مع غياب أخطاء closing connection الجديدة أثناء الاستخدام.
2. افتح العملاء والمتابعات والمهام اليومية والإشعارات والشاشات المالية المسموحة. قارن بيانات معروفة وحالة التحديث بالفترة والحساب الصحيحين. أصفار بطاقات الداشبورد في صورة سابقة ليست وحدها دليلًا على فقد البيانات أو صحتها، ولا تصلح كأساس لتعديل حساباتها.
3. بعد تحميل بيانات مسموحة، افحص عرضها offline ثم العودة online، والعودة للتبويب والتنقل العادي. راجع الأخطاء الجديدة وحالة الكاش، دون حذف بيانات الموقع أو قاعدة IndexedDB أو تغيير نسختها لافتعال فشل.
4. افحص حساب الإدارة وموظفًا محدودًا ومندوبًا وحسابًا بلا صلاحيات الشاشات المتأثرة، وتبديل الحسابات. يجب أن تبقى البيانات المفصولة حسب namespace والصلاحيات القائمة كما هي.
5. عند إجراء عملية عمل حقيقية مصرح بها، راجع حالة المزامنة القائمة. لا تنشئ راتبًا أو فاتورة أو مصروفًا أو حذفًا تجريبيًا لاختبار الكاش. SC1 لا يشغّل Offline Queue ولا يعيد إرسال عملياتها.
6. راجع العربية والإنجليزية وDesktop/Tablet/Mobile وLight/Dark. الملفات المرئية والترجمة وCSS بقيت مطابقة، والتحقق البصري الحي مطلوب.
7. راجع بقاء سلوك P3 وP4: قناة إشعارات واحدة في التبويب المتصل، وقناة التنفيذ مرتبطة بشاشتها. عدد القنوات وحده لا يثبت نجاح الاشتراك أو صحة البيانات.

`getConnectionStatus` قراءة سلبية لحالة الاتصال المعروفة والعدادات؛ حالة open ليست إثباتًا شاملًا للقراءة/الكتابة أو لسلامة كل بيانات المتصفح. في الحالة المعتادة يكون successfulOpens=1. إذا حدث إغلاق فعلي ثم تعافٍ، قد يزيد successfulOpens وinvalidations. العدادات تتصفّر عند reload. لا تعكس هذه العدادات SQL أو استهلاك Logs.

## Rollback — خطة التراجع

تراجع عن SC1 عند ظهور خلل جديد في الكاش أو تبديل المستخدم أو تحميل الشاشات مرتبط بالنشر:

1. احتفظ بالإصدار وحالة الاتصال ونتيجة الالتقاط ووصف الشاشة، دون مفاتيح أو بيانات عملاء.
2. اعكس commit SC1 وحده، أو أعد الملفات الستة المعدلة من commit 18.56.143 السابق، مع الاحتفاظ بأي تعديل مستقل معتمد. لا تستخدم نسخة أقدم من P5.
3. انشر الملفات الستة معًا؛ رقم الإصدار وPWA وservice worker وindex يجب أن تكون من نفس النسخة.
4. أعد تحميل البرنامج بالطريقة المعتادة وتحقق من 18.56.143 وسلامة الشاشات والإشعارات والتنفيذ. لا تمسح IndexedDB أو localStorage أو Offline Queue لمعالجة رقم إصدار قديم.
5. لا SQL ولا ترحيل schema للتراجع. قاعدة الكاش ونسختها متوافقتان مع النسخة السابقة. التراجع يعيد أيضًا عيب التعافي القديم؛ سجل ذلك عند تقييم النتيجة.

## المخاطر المتبقية والأعمال المفتوحة

- سبب الإغلاق الأول للـIndexedDB غير محسوم، وكذلك السبب الأول لاختفاء عميل Supabase قبل إعادة التحميل. الإصلاح يعالج تعافي الكاش المثبت فقط.
- إذا رفض المتصفح التخزين أو امتلأ قرصه أو حُذفت بياناته، لا يمكن ضمان استمرار البيانات في الذاكرة بعد reload. لا يوجد في SC1 إصلاح عام لتلف التخزين أو quota، ولا ضمان لاستعادة بيانات حُذفت خارجيًا.
- معاملة بدأت ثم أُلغيت لا تعاد تلقائيًا. تظل رسائل الفشل الأخرى مهمة؛ لا يخفي الإصلاح كل أخطاء التخزين.
- إصدار/حذف قاعدة من تبويب آخر يجعل هذه الصفحة تنتظر reload وتستخدم fallback، حتى لا تعطل عملية الإصدار الآخر.
- لم تُقَس نسبة توفير Logs أو الحمل بعد SC1. تحذيرات IndexedDB المحلية ليست دليلًا وحدها على Log Ingestion في Supabase.
- زيادة عداد payroll من 0 إلى 1 بين نتيجتي A وB، مع تأكيد البقاء على الداشبورد، ما زالت ملاحظة مفتوحة. لا يغلق SC1 اختبارات توقيت P5 أو يغير خدماتها. تستأنف مراجعتها بعد استقرار الكاش والاتصال.
- تحذيرات Security Definer View المتبقية ومراجعة دوال الصلاحيات وRLS مسار مستقل. SC1 لا يتراجع عن SQL الأمني الذي طبقه المستخدم ولا يغلق أي تحذير أمني.
