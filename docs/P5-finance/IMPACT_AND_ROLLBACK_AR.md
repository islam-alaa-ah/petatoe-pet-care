# تقرير P5-VISIBLE-FINANCE-READS — الإصدار 18.56.143

## الحالة والأساس

- الأساس: `18.56.142 / 185742`، بعد تحديث الإشعارات P3 وتحديث دورة حياة تنفيذ المواعيد P4، وهي النسخة التي قدّم المستخدم نتائج تشغيلها.
- تمت مطابقة ملفات P4 السبعة مع بصماتها المسجلة، ومطابقة محتويات حزمة P4 مع شجرة العمل قبل نسخها.
- بصمة ZIP أساس P4: `06bd75c9391c4cebb0bae12ca2fb3953ab3362a7066bb7001f26d43fe750f6b2`.
- التعديل مُجهّز واختُبر محليًا؛ لم يرفع المساعد أي ملف إلى GitHub ولم يُنفّذ أي SQL أو تغيير على Production في هذه المرحلة.
- الإصدار الناتج: `18.56.143 / 185743`، بتاريخ `2026-11-08`. التحديث الإجباري معطّل.

## Root Cause — السبب المثبت في الكود

1. سجلت خدمة خزينة السيارة مهمة `vehicle_treasury` تستدعي `load(snapshotFilters())` بلا شرط لفتح الشاشة. عند عدم فتحها سابقًا تكون الفلاتر فارغة، فيُطلب workspace بالنطاق المسموح الكامل بدل نطاق شاشة مفتوحة.
2. خزنت خدمة الرواتب العادية سياقات آخر زيارة لإدارة الرواتب وكشف الراتب وإدارة العمولات وكشف العمولة والمرجع ودليل الإضافات والخصومات. مهمة `refreshActiveContexts` كانت تعيد تحديث السياقات المحتفظ بها دون مطابقة الشاشة الظاهرة.
3. كررت خدمة رواتب SEA VIBE السلوك نفسه لخمس شاشات، باستخدام آخر شهر أو فترة تمت زيارتها.
4. يفحص محرك المزامنة `isActive` الاختياري في مسار `foreground` فقط. لذلك إضافة هذا الشرط إلى التسجيل وحده لا تحمي مسارات `online` و`offline-queue` و`retry`. وُضع التحقق داخل مهام الخدمات الثلاث لكل أسباب التشغيل، دون تغيير المحرك المشترك.

هذا يثبت وجود مسارات لقراءات خلفية غير لازمة للشاشات المغلقة. عينة المتصفح التي أرسلها المستخدم تتوافق مع وجود هذه الطلبات، لكنها لا تثبت أي شاشة كانت مفتوحة لحظة كل طلب. ولا تثبت سبب قفزتي Logs يومي 1 و2 نوفمبر أو مدة SQL داخل الخادم.

## Impact Analysis — السلوك بعد التغيير

يبدأ التحديث التلقائي في الخدمات الثلاث فقط إذا كان التطبيق online، والتبويب `visible`، ومسار التنقل يطابق الشاشة، وعنصر الشاشة موجودًا وغير `hidden`، والمستخدم له ملف نشط مطابق لهويته وصلاحية العرض الحالية. ويجب أن يكون السياق قد فُتح لهذا المستخدم؛ هذه الشروط لا تمنح صلاحيات جديدة.

| الحالة | السلوك |
| --- | --- |
| الداشبورد، قبل فتح شاشة مالية | لا تبدأ مهام الخدمات الثلاث قراءة workspace |
| الداشبورد، بعد زيارة الرواتب والخزينة | السياقات محفوظة لاستخدام الشاشة لاحقًا؛ أحداث lifecycle لا تعيد قراءتها |

| شاشة مالية ظاهرة + عودة للتبويب أو الاتصال | تحديث السياق المطابق فقط، وفق سياسة محرك المزامنة القائمة |
| تبويب مخفي أو offline | لا تبدأ قراءة lifecycle جديدة من الخدمات الثلاث |
| تبديل الحساب | لا تُستخدم سياقات الحساب السابق لبدء قراءة تلقائية |

| اكتمال Offline Queue على الداشبورد | معالجة العمليات وكتاباتها وإبطال الكاش تستمر؛ قراءة الخزينة التلقائية مؤجلة حتى تكون شاشتها ظاهرة |
| اكتمال المزامنة أثناء قراءة الخزينة الظاهرة | انتظار القراءة الحالية، ثم تحديث واحد بالفلاتر الحالية إذا بقيت الشاشة مؤهلة |

1. احتفظ بـcommit/ZIP الإصدار 18.56.142 الذي يعمل حاليًا.

## اختبارات Production المطلوبة

ابدأ بالمشاهدة والقراءة فقط. لا تنشئ راتبًا أو مصروفًا أو اعتمادًا تجريبيًا في Production. افحص الحفظ/المزامنة أثناء عملية عمل حقيقية ومصرّح بها مع مقارنة النتيجة المتوقعة، دون إعادة تنفيذ العملية لإثباتها.

1. **Administrator / super_admin:** تأكد من 18.56.143 وruntime P5 للخدمات الثلاث. على الداشبورد التقط الحالة، زر الخزينة والرواتب ثم ارجع وانتظر القراءات الجارية؛ التقط نقطة مقارنة جديدة. بعد تبديل التبويب والعودة، يجب ألا تزيد `refreshCalls` لهذه الخدمات ولا تبدأ workspace RPCs المستهدفة أثناء البقاء على الداشبورد.
2. **خزينة السيارة:** افتحها وتأكد من السيارات والنطاق والأرقام والفلاتر. اختبر تغيير السيارة والتاريخ والبحث والتحديث الصريح. عد للتبويب أثناء بقاء الخزينة مفتوحة وتأكد من قراءة النطاق الحالي وتحديث الشاشة.
3. **الرواتب العادية وSEA VIBE:** افتح كل شاشة مسموحة على حدة، واختر فترة معروفة ثم عد للتبويب. يجب أن تتحدث الشاشة الحالية فقط وبنفس الفترة. اختبر فتح دليل الإضافات/الخصومات وإغلاقه دون حفظ تجريبي. قارن البيانات المعروفة بالأساس وفق صلاحيات الحساب.
4. **الحسابات المحدودة:** موظف محدود، مندوب، حساب بلا صلاحية الرواتب/الخزينة، ثم خروج من الحساب. تأكد من عدم ظهور بيانات جديدة خارج صلاحياتهم، ومن عدم بدء مهام الخدمات الثلاث تلقائيًا عند رفض العرض. هذا فحص regression للواجهة؛ ليس بديلًا عن اختبار API/RLS في مسار Security.
5. **الانقطاع والتنقل:** بعد تحميل بيانات مسموحة، اختبر العرض من الكاش offline، ثم رجوع الاتصال على الداشبورد وعلى الشاشة المالية، والتنقل السريع أثناء طلب جارٍ. العمليات غير المكتملة تظل في Offline Queue وتُراجع حالتها دون مسح التخزين.
6. **وظائف العمل الفعلية:** عند حدوث حفظ مصروف أو مزامنة أو اعتماد راتب مصرح به، تأكد من اكتمال العملية مرة واحدة ومن تحديث الشاشة الظاهرة بعده، دون تغيير المبالغ أو حالة الاعتماد. الاختبارات المحلية تغطي المسارات، والتحقق الحي يظل مطلوبًا.
7. **الإشعارات والتنفيذ:** في التبويب المتصل، قناة إشعارات واحدة وفق P3. على شاشة التنفيذ قناة تنفيذ واحدة، وعلى الداشبورد صفر وفق P4. لا تضف تبويبات دائمة لقياس القنوات ثم تعتبر عددها على مستوى المشروع تكرارًا.
8. **العربية/الإنجليزية، Desktop/Tablet/Mobile، Light/Dark:** افتح الشاشات المتأثرة وتحقق من الفلاتر والأرقام والتحديث. لم تتغير CSS أو قوالب الواجهة أو الترجمة، لكن الاختبار البصري الحي مطلوب.

استخدم Network لفترة قصيرة محددة مع معرفة الشاشة الحالية؛ لا تعمم أسماء endpoints المتكررة وحدها. `refreshCalls` عدد استدعاءات تحديث تلقائي، وقد تتشارك الاستدعاءات قراءة واحدة عبر single-flight. و`pending` قد يشمل قراءة مباشرة قائمة. كل العدادات محلية لهذا التبويب وتتصفّر عند إعادة التحميل. إثبات خفض Logs يحتاج مقارنة نافذتين متماثلتين في النشاط، وليس مجرد اختفاء طلب أو رقم إصدار.

## Rollback — خطة التراجع

التراجع عن P5 يكون عند تعطل فتح شاشة أو فلاترها، اختلاف بيانات معروف بلا تفسير من الصلاحية/الفترة، فقد تحديث بعد حفظ/مزامنة فعلية، أو خطأ جديد من الخدمات الثلاث.

1. احفظ وصف الخطأ والإصدار والشاشة وحالة الشبكة ونتيجة الالتقاط دون نسخ بيانات مالية أو مفاتيح.
2. اعكس commit P5 وحده إذا لم يُدمج معه عمل آخر، أو أعد **الملفات الثمانية المعدلة فقط** من commit 18.56.142 الأصلي الذي سبق النشر. الملفات المضافة تقارير/اختبارات ولا تُحمّل في التطبيق؛ حذفها اختياري عند التراجع.
3. انشر الملفات الثمانية معًا بما فيها `index.html` و`pwa.js` و`service-worker.js` و`version.json`. لا تخلط بيانات إصدار من نسختين.
4. أعد تحميل التطبيق بالطريقة المعتادة وتحقق من 18.56.142، ومن فتح الخزينة والرواتب وعودة سلوكها السابق. إذا أعاق مسار تحديث التطبيق الرجوع لإصدار أقل، اتبع آلية النشر المعتمدة مع الاحتفاظ بالبيانات المحلية؛ لا تمسح site data لحل رقم الإصدار.
5. تحقق من استمرار P3 وP4: التنفيذ صفر خارج شاشته، والإشعارات تعمل. تراجع P5 لا يعيد تغييرات SQL الأمنية ولا يحتاج SQL.

## المخاطر المتبقية وشروط إغلاق المرحلة

- التحقق الحي لكل الأدوار والأجهزة لم يُنفّذ هنا. نتائج محلية ناجحة لا تكفي لإغلاق Production regression.
- الطلب الجاري قد ينتهي بعد المغادرة، والتحميل المباشر cache-first قد يعيد التحقق في الخلفية كما كان. هذه الحزمة تضبط المهام التلقائية الثلاث المحددة.
- لا تتغير آلية الكاش العامة أو كل حالات تبديل الحساب أثناء طلب بدأ بالفعل. حماية بدء هذه المهام بهوية صاحب السياق لا تعني اعتمادًا أمنيًا شاملًا للكاش أو RLS.
- لا توجد نسبة توفير مقاسة على Production، ولا نسبة يمكن نسبها لقفزتي 1 و2 نوفمبر من هذه المعطيات. أسباب بطء SQL/ضغط الخادم تحتاج أدلتها الخاصة.
