# P4-EXECUTION-REALTIME — تقرير الأثر والتسليم

**18.56.141 → 18.56.142 / Build 185742**. الحالة: مجهز ومختبر محليًا؛ تطبيق Production والتحقق الحي ينتظران المستخدم. التاريخ: 8 نوفمبر 2026، القاهرة.

## Root Cause

بدء startRequestRealtime من DOMContentLoaded في installation-execution.js جعل قناة التنفيذ موجودة حتى خارج شاشة التنفيذ. تحديثات ثلاثة جداول كانت تؤدي إلى load بعد debounce 250ms دون شرط الشاشة أو ظهور التبويب. نتيجة المستخدم في 8 نوفمبر 11:25:48 القاهرة أكدت execution=1 بينما view=dashboard، إلى جانب قناة إشعارات واحدة.

النتيجة نفسها أظهرت طلبات ناجحة استغرقت نحو 11–12 ثانية، لكن أزمنة المتصفح لا تفصل SQL عن الشبكة أو الانتظار، ولا تحدد سبب قفزتي Logs يومي 1 و2 نوفمبر. هذه الخطوة تعالج مصدر عمل خارج الشاشة، ولا تدعي علاج جميع أسباب البطء أو تجاوز Logs.

واجهتان غير متزامنتين كانتا تحتاجان معالجة صحيحة: InstallationsServiceSafe يعيد Promise تنتهي إلى دالة إغلاق، ودالة الإغلاق لم تكن تعيد Promise إزالة القناة. كما أن القراءة الاعتيادية cache-first قد تعيد النسخة القديمة فورًا بينما تحدثها في الخلفية؛ لذلك الرجوع للشاشة يحتاج خيار قراءة حديثة صريحًا مع fallback.

## Impact Analysis

| الجانب | السلوك الجديد وأثره |
|---|---|
| Dashboard وبقية الشاشات | قناة التنفيذ لا تبدأ من مجرد فتح التطبيق؛ لا تحديثات شاشة من callback قديم |
| التنفيذ المرئي لحساب مسموح | قناة تنفيذ واحدة لكل تبويب، وقراءة workspace/هوية حديثة عند التفعيل |
| مغادرة/إخفاء/الخروج | تعطيل جلسة الشاشة فورًا، إلغاء debounce، وإغلاق قناتها عند اكتمال عملية الفتح المعلقة |
| تنقل سريع | انتظار الإغلاق السابق قبل فتح قناة جديدة، وإهمال النتائج المتأخرة |
| تبديل المستخدم أو إلغاء الصلاحية | تفريغ بيانات التنفيذ المحلية ومنع نتيجة المستخدم السابق من الرسم؛ تستخدم الصلاحيات الحالية دون تعديل منطقها |
| Offline | استمرار قراءة الكاش والعمليات الآمنة القائمة كما يقررها service؛ لا قناة جديدة دون اتصال |
| فشل القراءة Online | الكاش المتاح يظل fallback ويُعرض بحالة cache الموجودة؛ دون ادعاء حداثة بيانات فشلت قراءتها |
| الإشعارات | ملفات P3 لم تتغير، ولا removeAllChannels أو قطع عام للـRealtime |

HTTP بدأ قبل مغادرة الشاشة قد يكمل ويحدّث كاش الخدمة الخاص بسياقه؛ لا نلغيه بالقوة لأن الخدمات مشتركة. حارس جلسة الشاشة يمنع رسمه بعد المغادرة أو تبديل الحساب. لا تفسر طلبًا معلقًا أكمل بعد الخروج على أنه قناة جديدة.

## Scope وMinimal Change

الملفات التشغيلية المعدلة سبعة:

1. **assets/js/installation-execution.js**: جلسة شاشة مرتبطة بالمستخدم والصلاحية والرؤية والاتصال؛ بدء/إغلاق متسلسلان؛ دمج دفعات الأحداث والقراءة الجارية؛ قراءة لاحقة للطلب الصريح أثناء read جارية؛ إهمال نتيجة الجلسة السابقة؛ getter تشخيصي لا يعرض الهوية.
2. **assets/js/installations-service.js**: ستة استبدالات محددة فقط: إعادة نتيجة removeChannel؛ إضافة force اختياري إلى قارئ الكاش؛ شرط انتظار الشبكة عند force؛ fallback للكاش عند فشل force؛ وتمرير الخيار في قارئي execution وexecutionIdentity. جميع المستدعين الذين لا يمررون force يحتفظون بسلوكهم السابق. استعلامات الجداول والفلاتر وSQL/RPCs نفسها لم تتغير.
3. **index.html**: علامات الكاش لثلاثة ملفات JS المعدلة فقط؛ عناصر الواجهة والنصوص وCSS كما هي.
4. **assets/js/pwa.js**: رقم CURRENT_VERSION فقط.
5. **service-worker.js**: CACHE_VERSION فقط.
6. **package.json**: رقم الإصدار فقط.
7. **version.json**: الإصدار والبناء وتاريخ وعنوان وملاحظات المرحلة بالعربية والإنجليزية؛ forceUpdate=false كما كان.

لم يُعدل أي SQL أو RLS أو EXECUTE أو دور، ولا أجسام وظائف التحصيل/الفواتير/الرواتب/العمولات أو صيغ العرض المالي. تحقق محلي قارن خدمة المواعيد كاملة وأثبت أن بقية محتواها مطابق بعد عزل الاستبدالات الستة، وقارن دوال واجهة التنفيذ القديمة دون تغيير إلا load وربط دورة الحياة والحقول اللازمة.

لم نعدل Sync Engine العام أو تحميل المهام والاقتراحات أو count العملاء أو خزينة السيارة أو الرواتب. قد يستمر تحديث سياقات محفوظة عند foreground/online عبر appointments_read أو الوحدات الأخرى؛ هذا بند مستقل من AUDIT-BACKEND-01، وليس فشلًا في إغلاق قناة الشاشة.

## الاختبارات المنفذة

- **27/27** اختبار Node VM محلي باستخدام المصدر المعدل وmocks، دون شبكة أو قاعدة بيانات: Dashboard/فتح التنفيذ، الصلاحيات وغياب الهوية، تكرار الأحداث، debounce، التحديث أثناء read، المغادرة قبل اكتمال الفتح، انتظار الإغلاق، إخفاء/إظهار التبويب، offline/online، الخروج من تبويب آخر، تبديل A إلى B مع نتيجة A المتأخرة، إلغاء الصلاحية، refresh صريح أثناء read، pagehide/pageshow، رفض الاشتراك، وتمرير Promise الإغلاق الحقيقية من الخدمة.
- من الاختبارات نفسها: قراءة execution/identity الحديثة تنتظر مصدر الشبكة، وفشلها يرجع الكاش، وOffline لا ينفذ قراءات جداول في المحاكاة، والمستدعي القديم دون force يحتفظ بسلوك cache-first.
- **16/16** اختبار P3 الوظيفي الحالي اجتازت دون تعديل ملفات الإشعارات. اختبار P3 التاريخي الذي يثبت رقم 18.56.141 استُبعد لأنه يختبر إصدارًا سابقًا؛ تشغيله دون استبعاد يرفض 18.56.142 كما هو متوقع. فُحص اتساق بيانات إصدار P4 مستقلاً. لا تستخدم preflight مرحلة قديمة لإثبات تثبيت إصدار أحدث.
- سبعة فحوص syntax لملفات JS/MJS المعدلة والمضافة، واتساق الإصدار 18.56.142 والبناء 185742 وكاش Service Worker وAR/EN.
- مقارنة **1162** ملف baseline المعاد بناؤه من ZIP الأصلي وحزمة P3؛ **1155** ملفًا بقيت مطابقة. جميع ملفات CSS الـ31 وSQL الـ422 مطابقة. ملفات الإشعارات P3 مطابقة.
- فحص preflight للسبعة ملفات اجتاز في وضع baseline على مصدر 18.56.141، وفي وضع installed على المصدر المعدل.

محاولة تشغيل Chromium محلي توقفت لأن البيئة منعت إنشاء socket بـEPERM. لذلك **لم تُنفذ اختبارات متصفح مرئية أو حسابات حية**، ولا نصف المحاكاة بأنها Regression حي ناجح. لا اتصال Production أو SQL نفذه المساعد، ولا إعادة فحص Security Advisor ضمن P4.

## ترتيب التنفيذ

1. تثبيت أحدث baseline: 18.56.141 مع P3 كما ظهر في قياس المستخدم. إذا عُدلت الملفات السبعة لاحقًا، أوقف الاستبدال وادمج على النسخة الأحدث.
2. حفظ آخر commit والسبعة ملفات قبل هذه المرحلة. لا DDL في الحزمة؛ لا SQL تنفيذ أو Rollback للقاعدة مطلوب.
3. رفع محتويات مجلد المرحلة بمساراتها الأصلية في commit واحد؛ باقي الملفات Added Only للتوثيق والفحص. لا تجمع معه إصلاحات أخرى.
4. انتظار اكتمال نشر الموقع، تحديث التطبيق والتحقق من 18.56.142 وruntime=P4، ثم التقاط الحالات أدناه بالسكربت المحلي المرفق.
5. مراجعة النتائج قبل أي خطوة تحسين تحميل أخرى. تبقى إصلاحات Security بمسارها المنفصل.

## Regression المطلوب على Production

| السيناريو | شرط القبول |
|---|---|
| Admin، موظف محدود، مندوب، بلا صلاحية التنفيذ، وanon | نطاق القراءة الحالي والبيانات المسموحة مستمران؛ غير المسموح لا يفتح قناة تنفيذ |
| Dashboard → التنفيذ → Dashboard | execution 0 → 1 → 0 بعد استقرار الإغلاق؛ قناة الإشعارات تستمر حسب الاتصال والحساب |
| تنفيذ → شاشة أخرى → تنفيذ بسرعة | لا قناتان مستمرتان ولا استثناء بسبب Promise cleanup؛ أحدث بيانات عند الرجوع |
| إخفاء التبويب والعودة | إغلاق الاشتراك أثناء الإخفاء وإعادة تفعيله إذا كانت شاشة التنفيذ هي الحالية |
| Offline/online وفتح شاشة من كاش موجود | بيانات الكاش قابلة للعرض، لا قناة offline، ومصالحة عند رجوع الشبكة؛ لا تمسح Offline Queue |
| خروج ودخول/تبديل حساب | لا بيانات مرسومة أو callback من الحساب السابق؛ نطاق المستخدم الجديد صحيح |
| متابعة تنفيذ طبيعي قائم | تحديث الحالات من العمل المشروع يظهر بالشاشة المفتوحة؛ لا إنشاء تحصيل أو فاتورة تجريبية لأجل الاختبار |
| إشعارات P3 | بقاء الجرس والتحديث وحالة القراءة؛ اختبار تسليم حدث حقيقي مشروع حسب خطة P3 السابقة، دون توليد إشعار اصطناعي غير مطلوب |
| AR/EN وDesktop/Tablet/Mobile وLight/Dark | القوائم والأزرار والتواريخ والقراءة مطابقة؛ لا تغيير تصميم أو ترجمة في هذه المرحلة |

السكربت scripts/p4-execution-live-readonly.js يقرأ الحالة الحالية فقط. channelAttached تعني أن الخدمة أعادت دالة إغلاق للقناة؛ اتصال Realtime الفعلي يُراجع من executionStates=joined، ولا يستنتج من هذا الحقل وحده. لا تختزل القبول في رقم الإصدار أو نجاح JSON.

## Rollback

تراجع مستقل عن P3 وSEC-S2.01/SEC-S3.01: أعد commit P4 وحده أو استعد الملفات التشغيلية السبعة من آخر baseline 18.56.141 المعتمد. احفظ أي تعديلات جاءت بعده، ولا تستبدل المشروع كله أو تشغّل SQL قديمًا. الأدوات والوثائق المضافة ليست جزءًا من تشغيل التطبيق ويمكن إبقاؤها كسجل.

بعد نشر التراجع أغلق تبويبات التطبيق القديمة وأعد تحميل الصفحة من الشبكة وفق المسار المعتاد، وتحقق من رقم الإصدار/الكاش؛ التراجع إلى manifest برقم أقل لا يضمن تحديث تبويب قديم تلقائيًا. لا localStorage.clear ولا IndexedDB/Clear Site Data؛ قد توجد معاملات غير مزامنة. سيعود السلوك القديم الذي يفتح قناة التنفيذ بالخلفية.

## المخاطر المتبقية

- تحقق SDK والإغلاق الفعلي على الأجهزة والحسابات الحالية منتظر؛ الإغلاق المتأخر يمنع فتح القناة الجديدة إلى أن تنتهي Promise القديمة. قد يتأخر التحديث الحي أثناء ذلك، مع بقاء قراءة الشاشة/زر التحديث متاحين.
- الشبكة غير المتاحة قد تعيد كاشًا أقدم؛ يظهر بحالة cache الحالية. لا تمثل هذه الحالة قراءة مؤكدة حديثة.
- هذا الإصلاح لا يقيس أو يضمن نسبة خفض Logs/CPU، ولا يفسر قفزات التاريخ السابق أو 11 ثانية انتظار لكل خدمة.
- بقية أحمال lifecycle والكاش والاقتراحات والعدّ ما زالت مراحل مستقلة.
- التحذيرات الأمنية السبعة المتبقية ودوال الصلاحيات وRLS لم تُغلق بهذه الحزمة؛ التغييرات الأمنية اليدوية السابقة لم تُلغَ.
