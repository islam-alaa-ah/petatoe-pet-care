CONFIRMED ROOT CAUSES / DEFECTS FOUND
1) CREATE APPOINTMENT — BLOCKER
   create_petatoe_appointment RETURNS TABLE(id uuid, request_number text).
   PL/pgSQL therefore has an output variable named "id".
   The function used: where id=p_neighborhood_id.
   This is ambiguous between the output variable and installation_neighborhoods.id and produces:
   column reference "id" is ambiguous.

2) UPDATE APPOINTMENT — SAME LATENT BLOCKER
   update_petatoe_appointment used the same unqualified neighborhood id expression.
   It would fail through the same path when editing an appointment.

3) SCHEDULING SLOT CONTRACT DRIFT
   Current UI/runtime still exposed 10:00 through 21:00 hourly slots.
   PETATOE canonical slots are 12:00 / 14:00 / 16:00 / 18:00 / 20:00 / 22:00.

4) 22:00 WAS IMPOSSIBLE IN SINGLE-DAY VALIDATION
   installations-service.js accepted hours only through 21:00, so the final 10 PM slot could not be saved.

5) MULTI-DAY SCHEDULING USED LEGACY 10:00 DEFAULTS AND HAD NO CANONICAL SLOT CHECK
   New multi-day visit seeds could start at 10:00 and the client did not restrict all visits to PETATOE slots.

6) TEAM MASTER / SCHEDULING INTEGRATION DRIFT
   Appointment teams are already groomer + driver + car, but scheduleTeams() only loaded id/name/status.
   Scheduling continued to require a manually typed technician name instead of using the groomer attached to the team.

7) DATABASE HAD NO PETATOE-SPECIFIC FIXED-SLOT GUARD
   Client defects or old clients could still write non-canonical schedule times.
